# Live verification — 2026-11-18 (B1: unavailable real browser)

Plugin: `dsh-webdev-viewer` working tree after the B1 change (package 0.1.1), Desktop
profile, DSH Desktop 0.2.2.0, Windows 11, `realBrowserEnabled: true`,
`cdpEndpoint: http://127.0.0.1:9222`.

The host half was reloaded live by toggling the bundle row (`include:ui-webdev`
via the plugin manager: disable → enable, `application: "applied"`); the client
half was rebuilt and reloaded with it. The panel was checked in a second DSH
client (headless Edge, 1470×905) whose tab showed the same GUI URL, driven over
raw CDP so the check did not disturb the user's browser.

## Healthy path (after reload)

- `/api/dsh-webdev-viewer/state` →
  `{"tabs":[{"id":"D62BA2E3…","url":"http://127.0.0.1:5173/","title":"Beavon 办公助手","origin":"adopted"}],
  "activeTabId":"D62BA2E3…","running":true,"mode":"cdp","cdpEndpoint":"http://127.0.0.1:9222","isolatedAvailable":true}`
- `webdev_tabs` returned the adopted tab (no root-level `lastError` in a healthy state).

## Unreachable endpoint (acceptance 1, 2, 4)

- `webdev_electron_attach http://127.0.0.1:9444` (nothing listening) failed with:

  ```
  Error: webdev.real_browser_unavailable: could not reach the real browser at
  http://127.0.0.1:9444 (econnrefused). … No isolated-browser fallback was
  attempted. {"code":"webdev.real_browser_unavailable","endpoint":"http://127.0.0.1:9444",
  "reason":"econnrefused","remediation":"…"}
  ```

- The state route then carried
  `lastError { code: webdev.real_browser_unavailable, reason: econnrefused,
  endpoint: http://127.0.0.1:9444, at, remediation, detail: "fetch failed" }`,
  `attempts: 2`, `running: false`; `GET /api/dsh-webdev-viewer/state` stayed 200.
- The panel rendered the zero state: **No browser connected**, mode *Real
  browser*, target `http://127.0.0.1:9444`, `Failed attempts: 2`, reason
  *Nothing is listening there*, the classified sentence, code + local time,
  remediation, detail, and the buttons **Retry** / **Open in isolated Chromium**.
  The status row showed a red **Disconnected** marker, not "Live".
- The first live pass used the pre-fix client: the zero state rendered, but the
  status row still said **Live** in green while nothing was connected. The status
  row was corrected (`Disconnected` with an error dot, `No browser` when idle) and
  the plugin reloaded before the final checks below.

## Explicit isolated browser (acceptance 1, 7)

- Clicking **Open in isolated Chromium** in the live panel launched the host's
  own Chromium (headless) with a throwaway profile and restored the last page
  URL the panel had shown. State: `mode: isolated`, `running: true`,
  `realBrowserConfigured: true`, one created tab; `lastError` cleared.
- The status row changed to **Isolated browser** (mode visible) and the trace
  footer recorded the restore navigation. No separate window was opened and no
  settings were edited.
- The mode chip becomes a button; clicking it (`title="Use the real browser"`)
  sent `use-configured`, disposed the isolated session and re-attached to
  `http://127.0.0.1:9222` (`mode: cdp`, adopted Beavon tab, no failure).

## Mid-session disconnect and recovery (acceptance 5)

- With the viewer attached to a second throwaway browser on `http://127.0.0.1:9444`,
  `Browser.close` was sent over CDP to that browser.
- The state route published `webdev.real_browser_disconnected`,
  `reason: econnrefused`, `running: false`, `attempts: 1` **224 ms** after the
  close. The panel showed **Disconnected**, target, one failed attempt, the
  disconnect sentence, code + time, remediation, and Retry / Open in isolated
  Chromium — no agent turn was needed for the panel to reach that state.
- Restarting the browser on the same port made the host re-attach by itself:
  `running: true`, one adopted `about:blank` tab, `lastError` gone, `attempts`
  absent. The panel showed **Live** again with no click.

## Desktop tools after the panel is gone (acceptance 6)

- `webdev_desktop_snapshot` with no mounted native panel returned immediately:

  ```
  Error: webdev.panel_not_mounted: no mounted WebDev Viewer panel owns the
  desktop view. Open the WebDev Viewer tab in the right sidebar (or switch it
  back to the desktop browser) and retry.
  ```

  The old path waited the 30 s native deadline on a detached socket.

## Launch-failure evidence (acceptance 3)

- `ChromeProcess.launch({ chromePath: <node binary> })` failed with
  `Chrome exited before its DevTools endpoint came up (exit code 9). … Browser
  output: … bad option: --headless=new` — the browser's own stderr is captured
  and quoted. With real Chrome/Edge stderr containing the crashpad/ACL text the
  same path reports `spawn_denied` and keeps that output as the state's `detail`.

## Follow-up: HiDPI mirror and agent style preview (same day)

- The CDP mirror frame pipeline was probed with a fake panel socket at a 1363×963 CSS viewport and
  `deviceScaleFactor: 1.5`. Before the fix, live screencast frames were **1132×800** (the old 1280×800
  cap downscaled the larger panel) and were the only frames on screen. After the fix, live frames are
  **1363×963** and a settled page is replaced by a **2045×1445** device-scale still; the wire `width`
  and `height` stay **1363×963**, so picks and input mapping are unchanged.
- `webdev_desktop_style` was used on the user's live native panel: `set` on `#est_cn` returned the
  before/after values and `temporary: true`; `webdev_desktop_screenshot` showed the change in the panel.
  This is the same runtime inline-style mechanism as the panel style inspector: no source file changed,
  and a reload discards it. Bing's visible pill is drawn by another layer/pseudo-element (`#est_cn`
  itself already had `border-radius: 0`), which is why the demo used a visible fill + square outline
  instead of a bare radius change.
